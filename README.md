# 웹캠 시선 추적 비교 — 공통 1회 보정 GUI

**2026-09-02 보정점 표시 수정:** 가장자리 점의 중심만 2.5%에 두던 계산을 수정했습니다. 이제 화면 크기별로 최소 48 CSS px 안쪽의 픽셀 좌표를 사용하고, 46px 원·외곽 강조·안전 여백 전체가 화면에 들어오는지 실제 배치 후 확인합니다. 보정점은 안내 문구보다 위에 표시됩니다. 서버가 계산해 브라우저에 표시한 동일 픽셀 좌표를 EyeTrax, GazeFollower, EyeGestures, WebGazer의 공통 초기 보정에 사용합니다.

웹캠 하나로 같은 9점 보정 데이터를 수집하고, 보정된 네 엔진을 버튼으로 바꾸면서 응시점을 표시합니다. 초기 보정 이후 WebGazer의 클릭·마우스 이동 기반 추가 학습은 기본으로 켜져 있습니다. 화면에는 시작·재보정·카메라 종료, 네 엔진 선택, 응시점, 웹캠과 고정 윤곽만 표시합니다. 기존 12점 평가·결과 저장·보정 기록 내보내기·수동 진단 버튼은 제거했습니다.

**이 수정본 앱·서버·웹캠·브라우저는 제작 과정에서 실행하지 않았습니다.** 문법 검사와 카메라 없는 모형 테스트만 수행했습니다. 실제 장치의 정확도와 전체 보정 성공 여부는 사용자가 실행해서 확인해야 합니다.

**이번 ZIP에는 실행용 브라우저 파일과 첫 실행용 모델을 포함했습니다.** 이전 ZIP의 누락 및 정상 0바이트 파일을 오류로 판단한 검사를 수정했습니다. Python 3.11과 `requirements.txt`의 라이브러리는 기존처럼 사용자가 설치합니다. Python/가상환경/OS별 pip 설치본 자체를 복사한 ZIP은 아닙니다. 이미 해당 환경이 설치돼 있으면 재설치할 필요 없습니다.

**Windows의 `site-packages/C:\...face_landmarker.task, errno=22` 오류도 수정했습니다.** Python에서 동봉 모델을 읽고 MediaPipe에 파일 내용(`model_asset_buffer`)만 전달합니다. EyeTrax의 원본 특징 추출·깜빡임 판정·Ridge 학습·예측은 그대로 상속하며 모델 생성 부분만 조정했습니다. 라이브러리 설치 파일이나 전역 함수를 수정하지 않습니다.

## 설치와 실행 — PyCharm

1. ZIP을 새 폴더에 풉니다.
2. PyCharm에서 **Python 3.11, 64비트 가상환경 하나**를 프로젝트 인터프리터로 지정합니다. 기존 Python 3.14는 그대로 두면 됩니다. 이 구성은 Python 3.14용이 아닙니다.
3. PyCharm 터미널의 Python이 같은 가상환경인지 확인하고 설치합니다.

```bash
python -m pip install -r requirements.txt
```

4. `run.py`를 PyCharm에서 실행하거나 다음 명령을 직접 실행합니다.

```bash
python run.py
```

5. 터미널의 **HTTP server READY** 메시지가 뜬 뒤 Chrome 또는 Edge에서 **http://127.0.0.1:8765/** 에 직접 접속합니다. **http://localhost:8765/** 도 사용할 수 있습니다. 포트를 바꿨다면 터미널에 표시된 주소를 사용하세요. 브라우저를 자동으로 열지 않습니다.
6. **시작 · 9점 보정** → 웹캠 허용 → 파란 점을 보고 **SPACE** → 다음 점에서도 반복합니다. 얼굴과 어깨가 보이도록 앉고 머리를 같은 자세로 유지하세요.
7. 완료 후 **EyeTrax / GazeFollower / EyeGestures / WebGazer** 버튼으로 바꿉니다. 추가 보정 화면은 나오지 않습니다. **WebGazer를 선택하고 빈 공간에서 커서를 보며 클릭·이동하면 추가 학습**합니다. 화면의 클릭/이동 횟수가 증가하는지 확인하세요.
8. 보정을 다시 할 때만 **재보정**을 누릅니다. **카메라 종료**는 스트림을 종료하고 보정 모델을 폐기합니다. 서버 종료는 터미널에서 Ctrl+C입니다.

WebGazer JS/회귀 모듈/소스맵, MediaPipe JS/WASM/그래프/데이터, EyeTrax의 `face_landmarker.task`, GazeFollower의 `base.mnn`을 ZIP에 포함했습니다. **`run.py`는 실행 파일이나 모델을 자동 다운로드하지 않습니다.** 이미 Python 패키지를 설치했다면 모델 다운로드를 기다릴 필요 없습니다. MediaPipe Python의 FaceMesh/실루엣 모델은 정상적인 `mediapipe==0.10.21` 설치본에 내장되어 있으며, `run.py`가 그 설치 파일도 모델 실행 전에 확인합니다. 브라우저 리소스와 카메라 요청은 localhost를 사용합니다.

앱을 시작하지 않고 압축 해제 상태만 확인하려면 `python verify_bundle.py`, 설치한 Python 패키지의 내장 모델도 확인하려면 `python verify_bundle.py --packages`를 사용하세요. 파일명·크기·SHA-256을 검사하며 웹캠/서버/모델을 실행하지 않습니다. **`face_mesh_solution_simd_wasm_bin.data`는 원본부터 0바이트인 정상 파일입니다.** 해당 파일의 존재와 원본 해시를 확인하므로 삭제된 파일이나 다른 모델이 잘린 경우와 구분합니다.

브라우저 파일을 직접 지웠다면 `python setup_envs.py --only webgazer`로 동봉 원본 아카이브에서 복원할 수 있습니다. 이 명령은 인터넷을 사용하지 않습니다. 모든 파일이 정상이라면 실행할 필요 없습니다. `python setup_envs.py`는 선택적 pip 설치 도우미이므로 Python 패키지를 내려받을 인터넷이 필요합니다. 미설치 패키지와 ZIP 파일 누락은 서로 다른 오류로 안내합니다.

`python run.py --port 8877`로 포트를 바꾸거나 `--samples 20`으로 점당 표본 수를 조절할 수 있습니다(10~60, 기본 30). 표본 수는 네 엔진 모두 동일합니다. Node/npm 설치는 필요하지 않습니다.

## 요청한 네 조건의 구현

| 조건 | 실제 동작 |
| --- | --- |
| 처음 한 번 보정 | 공통 9점, 기본 점당 30프레임으로 총 270개의 공동 유효 표본을 수집합니다. |
| 네 엔진에 동일하게 적용 | **같은 영상 프레임과 같은 목표 좌표**를 각 엔진의 특징 추출기·회귀 모델에 넣습니다. 엔진 간 내부 특징이 달라 **숫자 계수 자체는 공유할 수 없습니다.** 같은 사용자 보정 세션으로 각 모델을 한 번씩 학습합니다. |
| GUI 전환 | 버튼은 예측에 사용할 엔진만 바꿉니다. 초기 보정, WebGazer의 추가 학습 상태, 기준 자세를 초기화하지 않습니다. WebGazer는 선택 중인 동안 사용자 클릭·이동을 추가로 학습합니다. |
| 고정 머리·실루엣 | 첫 번째 공동 유효 보정 프레임에서 머리 윤곽과 사람 실루엣을 추출해 청록색으로 고정합니다. 웹캠 영상 위에 기본으로 계속 표시하며 숨김 옵션이 없습니다. |

브라우저가 웹캠 프레임을 캔버스에 한 번 복사합니다. WebGazer는 그 정지 캔버스를 읽고, 세 Python 엔진에는 **그 캔버스의 무손실 PNG**를 localhost로 전달합니다. 각 라이브러리가 요구하는 RGB/BGR 변환은 어댑터 안에서 수행합니다. 한 엔진이라도 유효한 특징을 만들지 못하면 그 프레임은 네 모델 모두의 학습 표본에서 제외됩니다. 첫 기준 윤곽을 추출하지 못한 경우도 제외하며, 화면에 대기 이유를 표시합니다.

모든 프레임의 승인 결과를 확인한 후 프레임 ID 목록이 일치할 때만 학습합니다. 수집 응답이 유실되면 같은 세션·같은 프레임 번호의 저장된 응답만 읽어 복구합니다. 모델을 다시 처리하거나 보정 표본을 중복 추가하지 않습니다. 정확한 응답이 없으면 중지하고 명시적 재보정을 요구합니다. 공통 초기 보정이 끝나면 WebGazer는 사용자 클릭·커서 이동을 추가 학습합니다. 엔진 전환 버튼 자체는 학습 표본에서 제외합니다. 추가 평가 화면은 없습니다. 탭을 숨기면 수집을 일시 중지하고, 돌아와 SPACE를 눌러 같은 보정 지점의 수집을 이어갈 수 있습니다.

**재보정 버튼만 9점 보정 절차를 새로 시작합니다.** WebGazer 온라인 학습은 이 버튼을 누르지 않아도 동작합니다. 페이지 새로고침·카메라 종료 후 재시작은 새 세션이므로 보정을 다시 해야 합니다. 보정 모델을 디스크나 브라우저 저장소에 저장·재사용하지 않습니다. 다른 탭에서 동시에 시작하지 마세요.

## 기준 자세를 보는 방법

- **청록색 실루엣 + 머리 윤곽:** 첫 공동 유효 보정 프레임에서 고정. 현재 영상의 움직임을 따라가지 않습니다.
- **흰색 머리 윤곽:** 현재 얼굴 위치. 추적 중 약 0.3초 간격으로 갱신합니다.
- **좌우·상하 수치:** 기준 머리 중심 대비 이동량을 카메라 영상 폭·높이의 백분율로 표시합니다. 좌우 부호는 거울처럼 보이는 미리보기 기준입니다.
- **머리 크기:** 기준 얼굴 폭을 100%로 본 현재 얼굴 폭입니다. 실제 거리(cm)나 머리 회전각 측정은 아닙니다.

기준 윤곽은 엔진을 바꿔도 유지되고 보정·추적 때 모두 보입니다. 이 표시용 윤곽으로 시선 예측을 추가 보정하지 않습니다. 각 엔진 자체의 머리 특징 처리는 유지합니다. 머리카락·어깨 등의 실루엣은 사람 분할 결과라 조명·배경에 따라 잘못 잡힐 수 있습니다.

## 사용하는 실제 엔진과 변경 범위

| 엔진 | 연결 방식 | 공통 보정을 위해 달라진 부분 |
| --- | --- | --- |
| EyeTrax 0.4.0 | 원본 `GazeEstimator` 특징 + 기본 Ridge | 공통 특징/좌표로 `train()` 1회. Windows 경로 문제를 피하기 위해 생성 시 MediaPipe 모델만 바이트로 전달 |
| GazeFollower 1.0.2 | 원본 MediaPipe 정렬 + MGazeNet 특징 + SVR | 자체 카메라/UI/HeuristicFilter 생략. 같은 좌표를 뷰포트 비율로 정규화해 원본 SVR 보정 1회 |
| EyeGestures 3.2.4 / v3 | 원본 눈·머리 특징 + 원본 Ridge(alpha=0.5) | 자체 25점 보정·백그라운드 재학습·출력 평균화 생략. 공통 데이터로 원본 X/Y Ridge를 한 번씩 학습 |
| WebGazer 3.5.3 | 원본 TFFaceMesh + 눈 영상 특징 + 원본 `RidgeReg.addData/predict` | 공통 초기 표본으로 시작한 뒤 클릭·마우스 이동을 원본 회귀 모델에 추가. 예측 때 계수를 갱신. 전체 초기 표본을 담기 위해 클릭 창 용량만 확장. 과거 세션 복원 및 Kalman 출력 필터는 사용하지 않음 |

EyeGestures는 기존 단일 환경 수정본과 같은 **3.2.4**입니다. **4.0.0 / Rust 버전이 아닙니다.** 서로 다른 환경을 자동으로 띄우지 않습니다. 네 엔진을 각각 원래 데모 설정 그대로 비교하는 벤치마크가 아니라, 공통 초기 보정과 WebGazer 추가 학습을 사용하는 비교 도구입니다. 눈 특징과 회귀 모델은 각 실제 라이브러리를 사용하며 같은 가짜 추정기를 이름만 바꾸지 않습니다.

## WebGazer 추가 학습의 범위

- 초기 보정 뒤 **WebGazer 선택 중**이면 클릭·마우스 이동의 화면 좌표와 최근 눈 영상을 원본 `RidgeReg.addData()`에 전달합니다. 원본 `predict()`가 갱신된 데이터로 회귀 계수를 계산합니다. 켜기 버튼은 따로 필요 없습니다.
- 다른 엔진을 선택한 동안에는 WebGazer 입력 수집을 쉬지만 학습된 데이터는 유지합니다. 다시 선택하면 그대로 이어집니다. 재보정·카메라 종료·새로고침은 새 세션이므로 추가 학습 데이터도 초기화합니다.
- 시작/종료/엔진 변경 같은 관리 버튼·선택 상자·링크 위의 이벤트, 보정 진행 중 이벤트, 숨긴 탭, 눈 특징이 없거나 영상 촬영 시점에서 500ms 이상 지난 이벤트는 학습에 넣지 않습니다. 일반 빈 공간에서 커서를 보며 클릭·이동하세요. 이동 표본은 원본 기본값처럼 최소 50ms 간격입니다.
- 원본의 50클릭 창에 초기 270개를 바로 넣으면 앞쪽 초기 보정이 버려지므로 **초기 표본 수+50**으로 창 용량을 늘렸습니다(기본 320). 이 창이 차면 원본 순환 버퍼 방식으로 오래된 표본부터 교체됩니다. 초기 보정 프레임 기록 자체는 별도로 유지하지만 모든 초기 특징이 영구히 회귀 모델에 남는 것은 아닙니다.
- 마우스 이동은 원본의 짧은 커서 이력(최근 1초, 저장 버퍼 10개)을 사용합니다. 데이터는 현재 세션의 메모리에만 있으며 버퍼 용량을 넘어 무한히 쌓지 않습니다. 브라우저 저장소에 영속 저장하지 않습니다.
- 클릭 위치가 실제 응시 위치라는 가정으로 학습하므로 사용량에 비례한 정확도 개선을 보장하지 않습니다. 다른 곳을 보며 클릭하면 나빠질 수도 있습니다.
- EyeTrax/GazeFollower의 일반 예측 경로에는 자동 온라인 학습이 없습니다. EyeGestures 3.2.4는 목표점이 있는 보정 모드의 반복 학습을 제공하므로 이번 변경에서 임의로 라이브러리에 없는 무라벨 학습을 추가하지 않았습니다. 세 Python 엔진의 기존 공통 초기 보정 경로는 그대로입니다.
- **기준 머리·실루엣은 온라인 학습 여부와 무관하게 항상 처음 것으로 고정됩니다.**

## 화면과 카메라 주의점

- 응시점 좌표는 **이 웹페이지 뷰포트의 CSS 픽셀**입니다. 전체화면에서 사용하면 화면 전체를 비교하기 편합니다. 다른 OS 프로그램 위에 뜨는 전역 오버레이는 아닙니다.
- 전체화면 요청을 거부해도 현재 브라우저 영역으로 보정할 수 있습니다. **창 크기·브라우저 확대율·전체화면 상태가 바뀌면 추적을 중지하며 자동 재보정하지 않습니다.** 재보정을 직접 누르세요. 모니터나 창 위치, 카메라 위치를 바꾸면 자동 감지가 되지 않을 수 있으므로 직접 재보정하세요.
- 화면 밖 좌표는 수치에서 자르지 않습니다. 응시점 그림만 가장자리로 제한하고 화면 밖 예측이라고 표시합니다.
- 카메라는 **브라우저만** 엽니다. Python의 `cv2.VideoCapture(0)`을 사용하지 않으므로 기존 WSL `/dev/video0` 오류 경로를 제거했습니다. 브라우저 카메라 권한과 Windows의 카메라 접근 설정은 허용해야 합니다.
- WSL 서버에 Windows 브라우저로 접속해도 카메라는 Windows 브라우저가 사용합니다. 다만 GazeFollower 패키지 import는 모니터 조회를 포함하므로 Python 측에 WSLg 등 그래픽/모니터 정보가 필요할 수 있습니다. 문제가 있으면 Windows용 Python 3.11/PyCharm에서 실행하세요.
- Zoom·Teams 등의 카메라 점유를 해제하세요. 카메라 목록 버튼으로 다른 장치를 고를 수 있습니다. 장치를 바꾸려면 카메라 종료 후 선택하고 다시 시작합니다.
- 카메라 영상은 localhost로 전송하고 메모리에서 처리합니다. 앱은 프레임·얼굴 사진을 파일에 저장하거나 외부 추론 서비스에 전송하지 않습니다. 고정 윤곽은 현재 세션 메모리에만 남습니다.

보정 중에는 네 엔진을 모두 처리하므로 느릴 수 있습니다. 추적 중에는 선택한 엔진만 시선 추론하고, 별도 머리 윤곽 검출도 수행합니다. 표시되는 처리 빈도에는 PNG 전송·브라우저/서버 왕복·윤곽 처리 비용이 포함되므로 각 라이브러리 단독 추론 속도와 같지 않습니다.

## Logger 초기화 오류 수정

GazeFollower의 메인 컨트롤러를 사용하지 않으면서 빠져 있던 `Log.init()`을 컴포넌트 생성 전에 호출하도록 수정했습니다. `Logger has not been initialized`가 떴다면 기존 `run.py`를 종료하고 이 ZIP의 코드로 다시 실행한 후 브라우저를 새로고침하세요. 재보정 버튼만 누르면 기존 코드가 계속 사용됩니다. 추가 패키지 설치는 필요 없습니다.

이후 다른 모델 오류가 발생하면 Python 터미널의 traceback과 `logs/gazefollower.log`에서 원래 원인을 확인할 수 있습니다. 이 파일에는 라이브러리의 진단 텍스트가 기록되며 웹캠 프레임을 저장하지 않습니다.

## Windows 모델 경로 오류 (`errno=22`)

모델이 실제로 존재해도 오류 경로가 `...site-packages/C:\Users\...\face_landmarker.task`처럼 두 경로를 이어 붙인 형태라면, 이번 로그처럼 MediaPipe의 네이티브 경로 처리에서 실패한 것입니다. 동봉 파일을 다시 다운로드하는 것으로 해결할 문제가 아닙니다.

수정본의 `BufferGazeEstimator`는 Python `Path.read_bytes()`로 모델 파일을 읽고, MediaPipe `BaseOptions(model_asset_buffer=...)`에 전달합니다. `model_asset_path`는 설정하지 않습니다. EyeTrax 0.4.0의 초기 상태와 FaceLandmarker 설정은 원본과 같고 특징 추출·학습·예측·종료 메서드는 원본을 그대로 상속합니다. 지원하지 않는 EyeTrax 버전에서는 조용히 다른 초기화를 적용하지 않고 버전 오류를 표시합니다. 관련 공식 API: [MediaPipe BaseOptions](https://ai.google.dev/edge/api/mediapipe/python/mp/tasks/BaseOptions).

기존 `run.py`를 종료하고 수정 ZIP 전체를 새 폴더에 풀어 다시 실행하세요. 브라우저도 새로고침해야 합니다. 시작이 실패한 뒤 이전 세션으로 `/api/end`를 보내던 후속 400 오류도 수정했습니다. `/.well-known/appspecific/com.chrome.devtools.json`의 404는 Chrome DevTools의 별도 요청이며 시선 추적 모델 누락이 아닙니다. 이 파일을 임의로 만들어 넣지 않습니다.

## ERR_CONNECTION_TIMED_OUT / Failed to fetch

`net::ERR_CONNECTION_TIMED_OUT`은 연결 시간이 초과됐다는 브라우저 오류입니다. **메시지 한 줄만으로 어떤 주소가 실패했는지, 모델 다운로드인지 localhost 연결인지 알 수 없습니다.** 패키지 미설치로 단정하거나 재설치부터 하지 마세요. 이 수정본은 실패한 요청 주소를 표시하고 원인을 구분하는 진단을 추가한 것이며, 사용자 환경의 연결 오류가 해결됐다고 검증한 것은 아닙니다.

1. 기존 `run.py`를 종료하고 수정 ZIP 전체를 새 폴더에 풀어 실행합니다. `HTTP server READY` 이전에는 서버에 접속할 수 없습니다. 이번 ZIP은 파일/모델 자동 다운로드 단계가 없습니다. 파일 누락이 안내되면 `python verify_bundle.py`로 압축 해제 상태를 확인하세요.
2. 서버를 실행한 컴퓨터의 브라우저에서 터미널에 나온 HTTP 주소를 엽니다. 기본은 `http://127.0.0.1:8765/`, 대체 주소는 `http://localhost:8765/`입니다. 포트를 바꿨다면 터미널의 주소를 사용하세요. PyCharm HTML 미리보기 주소나 `file:///.../index.html`, HTTPS 주소로 열지 마세요.
3. `/api/frame` 연결/응답 시간 초과 시 **동일 프레임의 저장된 응답을 읽어 복구**합니다. 복구할 수 없으면 서버 상태를 한 번 확인하고 오류 문장에 덧붙입니다. 수동 진단 버튼은 없습니다. 서버가 이미 보정 표본을 받았을 수 있으므로 POST를 자동 재전송하지 않습니다.
4. 계속 실패하면 `logs` 폴더와 PyCharm의 마지막 종료 코드를 확인하세요. 브라우저에서 요청별 세부 상태를 확인하려면 **F12 → Network → 빨간 요청 → Headers → Request URL**을 확인하세요. 오류 문장과 해당 전체 주소가 함께 있어야 다음 수정 지점을 정할 수 있습니다. 주소의 개인 토큰/인증 값은 공유하지 마세요.

| 진단 결과 | 확인할 사항 |
| --- | --- |
| `/api/health`도 응답 없음 | Python 프로세스, READY 메시지, 접속 포트, 같은 컴퓨터인지 확인. 브라우저와 Python이 Windows/WSL로 나뉘어 있다면 그 환경 정보도 함께 확인. |
| `/api/health`는 정상, `/api/start` 또는 `/api/frame` 실패 | HTTP 서버는 응답하지만 모델 처리까지 성공했다는 뜻은 아님. Python traceback과 아래 자동 로그 확인. |
| `/vendor/` 또는 `/mediapipe/` 파일 404/원본과 크기 불일치 | ZIP 전체 재해제 또는 `python setup_envs.py --only webgazer`로 동봉 파일 복원. 원본부터 0바이트인 `.data`는 정상. Python 라이브러리 전체 재설치는 불필요. |
| `/api/health` 404 | 이전 버전 서버 또는 다른 프로그램에 접속했을 수 있음. 기존 서버 종료 후 수정 ZIP의 `run.py` 재실행. |
| 외부 도메인 요청 실패 | 실제 URL과 Network의 Initiator 확인. 앱의 WebGazer는 로컬 MediaPipe 경로를 사용하며, 메시지만으로 외부 요청의 원인을 특정할 수 없음. |

일반 연결/파일 진단은 요청당 10초, 모델 API 응답은 최대 180초를 기다립니다(종료 요청은 10초). **HTTP 대기를 중단해도 Python에서 이미 시작한 작업이 취소되지는 않습니다.** 중복 보정 표본이나 중복 저장을 피하기 위해 POST를 자동 재시도하지 않습니다. 응답이 유실된 보정은 그대로 이어가지 않고 사용자가 재보정해야 합니다. 진단 성공은 파일 HTTP 응답 확인일 뿐 WASM 실행/그래픽 드라이버/카메라/정확도 검증이 아닙니다. WebGazer 내부 요청 등 모든 브라우저 오류가 JavaScript에 노출되는 것은 아니므로 필요한 경우 Network 탭을 확인해야 합니다.

서버는 계속 `127.0.0.1`에만 바인딩합니다. 이 수정은 방화벽을 끄거나 LAN 전체에 서버를 노출하지 않습니다.

개발 중 Python/GUI 소스를 직접 수정할 수 있습니다. `run.py`는 사용자의 소스 변경 자체를 차단하지 않고 실행 리소스의 무결성을 검사합니다. `verify_bundle.py`의 엄격 검사는 직접 수정한 파일도 원본과 다르다고 보고합니다. 수정본을 새 배포본으로 만들려면 `python build_zip.py`로 파일 목록/해시와 ZIP을 함께 다시 생성하세요. 기존 ZIP을 덮어쓰므로 원본을 보관하려면 먼저 복사하세요.

참고: [Chromium 네트워크 오류 정의](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/base/net_error_list.h), [Microsoft WSL 네트워크 안내](https://learn.microsoft.com/en-us/windows/wsl/networking).


## 자동 로그 — 별도 버튼 없음

`run.py`를 실행하면 프로젝트의 `logs/` 폴더에 기록합니다. 새 패키지는 필요 없습니다.

| 파일 | 기록 내용 |
| --- | --- |
| `runtime.log` | Python 예외, HTTP 처리 오류, 프레임별 응답 전송 결과, 서버 시작/종료 |
| `last_operation.json` | 마지막 요청 경로·프레임 순번·처리 단계·엔진 이름·시간·상태. 모델 호출 직전에 파일로 기록 |
| `last_operation.previous.json` | 서버 재시작 직전의 마지막 단계 보관 |
| `native_fault.log` | Python faulthandler가 포착 가능한 네이티브 충돌의 스레드 스택. 요청이 60초 이상 걸리면 중단하지 않고 스택 1회 기록 |
| `gazefollower.log` | GazeFollower 자체 로거의 진단 메시지 |

로그에는 요청의 PNG 영상, 얼굴 사진, 눈 특징, 보정 좌표, 인증 토큰을 기록하지 않습니다. Traceback에는 사용자 PC의 파일 경로가 들어갈 수 있습니다. 공유 전 개인 경로를 확인하세요. `runtime.log`와 `native_fault.log`는 크기에 따라 이전 파일을 하나 보관합니다. 마지막 단계 JSON은 현재/직전 실행만 보관합니다.

**현재 보내준 MediaPipe 경고·pygame 안내·Chrome DevTools 404·`MNN use low precision` 로그만으로 `/api/frame` 실패 원인은 확정되지 않았습니다.** 마지막 엔진 이름은 마지막으로 들어간 처리 단계이며 그 라이브러리의 결함을 확정하는 증거는 아닙니다. 서버 상태 요청도 실패했다는 사실만으로 프로세스 종료를 확정하지 않습니다.

Python 예외는 보통 HTTP 400/500에 원문을 포함합니다. 네이티브 충돌·프로세스 강제 종료·응답 중 연결 단절은 정상 JSON을 보내지 못할 수 있습니다. faulthandler도 모든 종료 원인을 잡지는 못합니다. 오류가 재발하면 `runtime.log`, `last_operation.json`, `native_fault.log`와 PyCharm 종료 코드를 확인하세요. 이미 서버를 재시작했다면 `last_operation.previous.json`도 확인합니다. 60초 스택 기록은 정지 원인 조사용이며 모델 강제 종료나 자동 재보정을 하지 않습니다. 브라우저 요청 제한은 기존처럼 180초입니다.

공식 참고: [Python 3.11 faulthandler](https://docs.python.org/3.11/library/faulthandler.html).


## 완료된 프레임의 응답 복구

리비전: `2026-08-31-frame-reply-recovery-1`

첨부한 로그는 프레임 55의 모델 처리 완료와 이후 서버 종료만 기록하고, 예외/네이티브 충돌은 기록하지 않았습니다. 이것만으로 실패한 요청이 프레임 55인지 다음 프레임인지, 실제 연결 실패 원인이 무엇인지 확정할 수 없습니다. 확인된 코드 결함은 응답 쓰기 중 `BrokenPipeError`/`ConnectionResetError`를 기록 없이 무시했던 부분입니다.

이번 수정은 다음과 같이 동작합니다.

1. Python이 처리한 프레임의 JSON 응답을 **전송하기 전에** 메모리에 보관합니다. 최근 4개만 보관하며, 입력 PNG나 학습 특징을 복구 캐시에 저장하지 않습니다.
2. 브라우저에서 연결/본문 수신 실패가 나면 `/api/frame-result?seq=번호`를 GET으로 조회합니다. 세션 ID와 인증 토큰은 헤더로 전달하고, 같은 세션·같은 번호·유효한 응답 형식일 때만 적용합니다. GET은 모델 작업 스레드를 거치지 않습니다.
3. 복구는 최대 4회, 회당 HTTP 대기 한도 3초입니다. 실제 모델 오류 HTTP 400/500은 정상 응답으로 바꾸지 않습니다. 없는 프레임을 이전 프레임으로 대체하지 않으며 PNG POST를 재전송하지 않습니다.
4. 보정 때 브라우저가 보관하던 해당 프레임의 WebGazer 특징에 **원래 승인 응답을 한 번만** 적용합니다. 초기 보정 표본·고정 윤곽·추가 학습 상태는 재생성하지 않습니다. 새 보정/세션 종료 시 응답 캐시도 삭제합니다.
5. HTTP/1.1 연결을 재사용하고 모든 JSON 응답에 실제 UTF-8 바이트 길이를 명시합니다. 거부해서 본문을 읽지 않은 POST는 연결을 닫아 다음 요청으로 오인하지 않습니다. 공식 참고: [Python HTTP server](https://docs.python.org/3.11/library/http.server.html#http.server.BaseHTTPRequestHandler.protocol_version).

`last_operation.json`의 `processed`는 모델 처리와 JSON 생성이 끝났다는 뜻입니다. 브라우저가 수신했다고 주장하지 않습니다. `runtime.log`에는 같은 프레임 번호로 `server_write_completed` 또는 `write_failed`가 기록됩니다. 전자는 서버 소켓 쓰기 완료이며 브라우저의 JSON 수신 확인과 다릅니다. 후자는 예외 traceback도 기록하고 끊긴 연결에 오류 응답을 덧붙여 보내지 않습니다.

서버가 받은 적 없는 요청, 계속 끊기는 연결, 실제 모델 오류까지 복구하는 기능은 아닙니다. 이러한 경우 실패를 표시합니다. 사용자 PC의 원래 연결 문제를 실제로 재현하거나 해결했다고 검증한 것은 아닙니다. 기본 접속 주소는 터미널에 표시되는 `http://127.0.0.1:8765/`입니다.
